# 主方法正文补全（默认关闭）

`AGENT_DIRECTED_EVIDENCE_ENABLED` 仍默认关闭。关闭时继续使用原检索、Planner、最终回答及修复消息合同；本轮没有更改模型或容量默认值。Agent 默认容量为 8，RAG 为 5，显式容量仍有效。

开启时，准备阶段先登记问题或已执行工具明确涉及的、已有权威源码证明的代码块覆盖，再检查名称是否可靠。对已确认的显式函数/方法，先补齐已持有的部分正文，再处理缺失目标、构造及间接调用。补全沿 Candidate → 权威回读 → EvidenceStore 同身份覆盖更新，不新增同一代码块的 Evidence 槽位，不改变引用身份。读取仍占共享次数、行数、字节和时间预算；超过单读 200 行的正文不会拆分绕限。

名称歧义不抹掉已知身份及部分正文，但也不授权补齐所有同名候选。有限 overload 规则只接受同一直接、无条件作用域中：静态确认的 `typing.overload`（含明确导入别名）、仅 `pass` 或 `...` 的声明、随后唯一无装饰实现。多实现、条件定义、重绑定或未知装饰器保持保守。已定位源码不证明运行期绑定，也不求解继承/MRO或动态分派。

仅提到类名或方法所属类不触发构造补读。明确的 `Class()`、`Class.__init__`、目标附近的有限构造用语，或可靠静态 `Class()` 调用关系仍可补证。大类回落构造也必须通过同一声明检查；不选择被重绑定、条件覆盖或未知装饰的旧构造。复杂自然语言或静态绑定不确定时，保留原 Planner 工具路径。

开启消息使用诊断协议版本 3；Planner Prompt 为 `rn-lwb-03-v14`，最终为 `m1-v6`，现有最终修复为 `m1-v6-repair1`。版本变化用于解释阶段覆盖及候选声明与调用绑定的区别，关闭路径仍为 `rn-lwb-03-v11` / `m1-v3` / `m1-v3-repair1`。

- `held_body_status` / `held_coverage`：仍有有效身份和源码证明的已持有覆盖。
- `delivery_status` / `delivered_coverage`：这一次序列化请求实际入选正文的覆盖；被筛除不等于从未取得。
- `binding_status`：静态声明检查结果，与正文覆盖独立。
- `body_read` / `read_committed`：发生权威正文读取但交付预算阻止更新时，保留已读与未提交的区别。
- `reason`：实际预算、截止、取消、权威拒绝或阶段筛选原因。`records_omitted` 与 `may_be_incomplete` 保留省略及范围边界。

诊断按请求内规范代码块合并，主方法优先，最多 32 条及 8192 字节，并使用消息预算的剩余空间。正文先占预算；诊断不能挤掉正文、创建 Evidence 或获得引用资格。普通请求和既有修复请求均使用实际入选正文投影。无诊断、完整正文或静态定位成功都不表示整道题的依据充分。

本轮只有隔离离线验证。长期测试及公开源码夹具位于 `backend/tests/test_main_method_completion.py` 和 `backend/tests/fixtures/main_method*_click.json`，不依赖 output 目录。测试中的脚本回答不证明真实模型质量。临时启用仅需在后续获授权进程中设置该开关为 `1`；撤销该进程变量或置 `0` 恢复，不必修改真实 `.env` 或持久环境。

2026-10-15 辅助依据修复：开启路径也识别问题或已执行工具明确请求的类数据成员限定名。若其类声明唯一、该成员在类体直接且无条件赋值一次，则将所属类的规范声明正文作为显式目标，在所有已持有主方法补全之后、普通调用外扩之前读取。例如中性场景 `Priority.LOW` 可以请求 `Priority` 的声明，而仅提到 `Priority` 不请求构造。多个成员复用同一代码块；类数据声明不会变成遍历整类所有方法的种子。单独明确请求构造时保留原构造路径。

此规则取得的是声明源码，不证明成员的运行期值、继承绑定或动态接收者类型。多个同名类、条件赋值、重绑定、未知装饰器、显式 metaclass、仅继承而无直接声明的成员均保守回退；不凭参数类型注解绑定 `ctx.method()`。超出 200 行的声明不拆读，也不因数据成员请求转读构造。容量、字节、共享次数和交付检查仍适用，不能挤掉完整主方法正文。未解决的动态方法调用及其他缺口继续如实交付；新增规则不保证整题依据充分。

上述数据成员修复本身未更改诊断字段、Prompt 或模型合同；后续候选反馈的版本变化见下文。新增离线用例见 `backend/tests/test_auxiliary_evidence_selection.py` 与 `backend/tests/fixtures/auxiliary_source_cases.json`；真实模型是否因此答对未在此次离线修复中验证。

2026-10-15 剩余候选源码检查：候选定义发现与运行绑定证明分开。开启路径可对已选择主方法中尚未解析的 `parameter.method()`，利用简单参数注解及明确导入找到该注解类**直接声明**的候选方法。注解只用于寻找源码，不证明实际对象类型；不追踪继承/MRO、复杂类型表达式或外部实现。唯一源码候选也不是唯一运行目标；多声明有界列出，不能挑最后定义或最长正文。

这些信息进入原有有界诊断的 `candidate_definitions`，包含来源、规范定义范围/哈希/revision、发现依据及 `runtime_binding_proven=false`。每处最多2个候选，保留省略标记；不是新Evidence，不自动读取或扩展候选，也不授予引用资格。普通和修复请求使用同一规则。诊断版本3及仅开启时的Prompt版本增量只解释这项新增合同，不改变回答策略。

所有显式主方法及显式数据声明处理后，若仍有未持有完整正文的注解候选，则暂缓普通调用外扩，给原有Planner工具保留剩余额度和槽位。不是额外预留额度或增加预算；余量为0仍如实回退。Planner可选精确符号检索，或在同文件/revision且范围合法时使用既有 `read_source` 一次取得多个相邻定义。该读取仍计1次完整范围及字节，最多新增2条各自规范Evidence；不能用它扩大200行/字节/容量限制。

候选源码即使通过权威回读和引用校验，也只证明所引代码块的身份。实际调用绑定仍可能未知。没有作出工具选择时不会声称正文已经取得；容量或选择预算排除时仍以实际Planner/final正文为准。长期离线保护见 `backend/tests/test_candidate_source_review.py`。本次未验证真实Planner会选中候选或真实答案会改善，默认仍关闭。
